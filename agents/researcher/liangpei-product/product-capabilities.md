# 良配产品形态 · AI 能力拆解

> 基于公开来源整理的良配三大 AI 能力（红娘 / 分身 / 军师）+ 1v1 匹配的产品形态。
> 本文档是事实**整理**，不是事实**验证**——核实结论见 [`fact-verification.md`](./fact-verification.md)。

---

## 一、AI 红娘

### 公开描述

> 「平台首个差异化 AI 能力」——用户在注册阶段或匹配初期，与 AI 红娘进行对话，红娘帮助用户完善资料、解读匹配对象、提供情感陪伴。

### 公开来源中提及的特征

| 特征 | 来源 | 核实状态 |
|---|---|---|
| 语音对话形式 | 36kr（创始人口述） | ⚠️ unverified |
| 20-30 分钟完成 onboarding | 36kr | ⚠️ unverified |
| 自动生成用户择偶画像 | 36kr | ⚠️ unverified |

### 复刻方案设计（基于已验证能力 + 一人可行性）

**MVP 形态**：
- **文本对话优先**（语音作为 M2+ 增强）
- 系统提示词：「温暖、倾听、不替用户决策、避免浮夸」
- 限定场景：注册引导、匹配解读、情感倾诉
- 不替用户做「你该和他在一起」之类决策

**人设参考**：参照婚恋节目主持人风格（如《非诚勿扰》孟非），不参照恋爱脑/霸道总裁。

## 二、AI 分身

### 公开描述（✅ 已核实）

| 核实点 | 描述 |
|---|---|
| 匿名提问 | 用户可向潜在匹配对象的 AI 分身匿名提问 |
| 敏感话题 | 资产/负债/情史/健康/彩礼/生育观等 |
| 对方身份保护 | 被提问方不知道具体提问者身份 |
| 真实回答原则 | 分身无法回答时如实告知，**不编造** |

### 训练机制推测

公开来源**未**明确披露训练数据来源与生成机制。基于行业惯例推测：

| 环节 | 可能方案 |
|---|---|
| 数据源 | 用户公开资料 + 价值观问卷 + 红娘代聊样本（**不**使用 IM 私聊原文，涉及隐私）|
| 风格锁定 | Few-shot prompt 嵌入用户填写的「说话风格 8 题」 |
| 一致性保证 | 风格样本向量检索 + LLM 生成 + 内容审核 |
| 防止滥用 | 单用户每日被提问上限 50 次 |

### 复刻方案

详见 `agents/architect/architecture/03-components-ai.md` 3.2 节（架构师已交付）。

**关键约束**：
- 不使用 IM 私聊原文（隐私 + 监管）
- 训练样本最小化（仅公开授权内容）
- 用户可一键删除分身
- 合成水印 + 可追溯

## 三、AI 军师

### 公开描述

> 「AI 军师」名称在多家媒体中被提及，但**功能定义模糊**。

### 复刻方案推测

基于「军师」语义 + 婚恋场景，推测为：

**关系诊断**——双方在 IM 私聊 30 条以上后，用户主动邀请 AI 军师分析：

| 输出 | 内容 |
|---|---|
| 兴趣度评分 | 0-100 三档（高/中/低）|
| 下一步建议 | 3 条具体话题/动作 |
| 风险提示 | 冷暴力 / 情绪异常等 |
| 决策边界 | 「这只是分析，决定权在你」 |

**对比 AI 红娘**：

| | 红娘 | 军师 |
|---|---|---|
| 时机 | 注册 / 匹配前后 | 私聊 30+ 条后 |
| 输入 | 用户自述 | IM 私聊文本 |
| 输出 | 陪伴 + 引导 + 解读 | 诊断 + 建议 |
| 风格 | 温暖 | 中立 |

## 四、1v1 匹配机制（✅ 已核实）

### 核心规则

> 用户进入匹配后**同时只能与一名匹配对象聊天**，确认对方不合适后才能解除匹配、了解其他人。

### 与 Tinder 式滑卡的差异

| 维度 | Tinder / 探探 | 良配 |
|---|---|---|
| 同时匹配数 | 不限 | **强制 1** |
| 决策压力 | 低（可以并行聊多人）| 高（必须认真对待当前） |
| 转化率 | 大量「养鱼」| 强制深入了解 |
| 用户体验 | 消费型 | 决策型 |
| 留存 | 短期峰值 | 长期沉淀 |

### 复刻方案关键设计点

```sql
-- matches 表的 source=1 表示自动匹配，status=2 表示已解除
-- matches 表的 status=1 表示当前进行中
-- 用户的 active_match_id 字段强制为单值
ALTER TABLE users ADD COLUMN active_match_id BIGINT;
ALTER TABLE users ADD CONSTRAINT only_one_active_match 
  CHECK (active_match_id IS NULL OR active_match_id > 0);
```

> 一个用户最多只能有一个 status=1 的 matches 行。架构师 Agent 已在 `agents/architect/modules/02-matching.md` 体现。

## 五、AI 搜索实验室（✅ 已核实）

### 5 维度

```
性格 | 学历 | 工作 | MBTI | 生活习惯
```

### 复刻方案设计点

| 维度 | 实现 |
|---|---|
| 性格 | 9 选 3 标签（外向/内向/理性/感性/…）|
| 学历 | 下拉选择（高中-博士）|
| 工作 | 自由输入 + 自动归类（IT/金融/教师/…）|
| MBTI | 16 型选择（可选填）|
| 生活习惯 | 多选标签（早睡/咖啡/运动/…）|

> 与传统婚恋的「身高体重年龄」硬筛不同，良配强调**软维度**——这与「严肃婚恋」的产品定位一致。

## 七、对架构师 Agent 的建议

| 调研结论 | 建议 |
|---|---|
| 1v1 机制是产品护城河 | 匹配引擎必须强制 1v1，不做滑动池 |
| AI 能力边界不明确 | 复刻版按「温暖倾听 + 资料解读 + 关系诊断」起步 |
| AI 分身需考虑隐私 | 训练数据严禁使用 IM 私聊原文 |
| AI 红娘 = 注册期核心 | 用户首次体验设计为红娘对话，而非资料表 |
