## 调研背景

### 为什么调研

复刻一个产品前，必须了解：

1. **产品的真实形态**——避免复刻错方向
2. **哪些是营销话术、哪些是可验证事实**——避免被创始人 PR 误导
3. **哪些是技术差异化**——明确复刻的护城河

### 调研方法

`/deep-research` 工作流：

```
Phase 1:  Scope   - 拆解为 5 个搜索角度
Phase 2:  Search  - 5 个并行 WebSearch
Phase 3:  Fetch   - 去重抓取 top 15 来源
Phase 4:  Verify  - 每条声明 3 票对抗核查
Phase 5:  Synthesize - 合并去重 + 置信度排序 + 引用
```

> 详见 `../method/deep-research-workflow.md`

## 核心结论摘要

### ✅ 已核实（≥2 票独立来源）

| 事实 | 主要来源 |
|---|---|
| AI 搜索实验室 5 维度（性格/学历/工作/MBTI/生活习惯） | 腾讯应用商店 |
| AI 分身匿名代问敏感话题（资产/彩礼/健康） | 36kr + c114 |
| 1v1 匹配机制（一次只与一位聊天） | 36kr |
| ¥2000 保结婚会员 + 3 年未领证全额退款 | 36kr（创始人受访） |

### ❌ 被反驳（仅 1 票 / 缺乏独立验证）

| 事实 | 驳回原因 |
|---|---|
| 「AI 红娘 20 分钟建档 / 463 字资料 / 82% 完成率」 | 仅单一 36kr 来源（创始人口述），无独立数据 |
| LangGraph 7 节点 / MongoDB+ES+ChromaDB 架构 | 第三方 GitHub 仓库的猜测，反向证据推翻 |
| 平台用户资料长度 463 字 vs 传统 132 字 | 同一来源反复出现，视为营销话术 |

### ⚠️ 未确认（仅有 1 票）

- 2026-07-04 上线时间（搜狐转载）
- AI 红娘 / 军师 的具体对话模式与边界
- 平台 MAU / 留存等运营数据

## 调研对复刻方案的影响

| 调研结论 | 对架构师 Agent 的建议 |
|---|---|
| 1v1 机制是产品护城河 | 匹配引擎必须强制 1v1，不能借鉴 Tinder 式滑动 |
| ¥2000 保结婚会员是真实验证 | 商业模式必须配套「履约保障基金」或保险机制 |
| AI 红娘能力边界不公开 | 复刻版按「温暖倾听型聊天机器人」起步，逐步迭代 |
| 监管复杂（婚介 + AI） | 算法备案 + 婚介资质必须 M0 启动 |

## 使用方式

- **架构师**：写技术方案时引用 `product-capabilities.md` 描述产品形态
- **产品分析师**：写 PRD 时参考 `fact-verification.md` 区分事实与推测
- **财务顾问**：商业模型评估基于 `business-model.md` 中的真实数字
- **QA 工程师**：`fact-verification.md` 中被反驳的事实是边界测试场景
